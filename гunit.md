Юнит-экономика на странице «Клиенты и расчёты»
Context
Страница клиентов сегодня отвечает только на вопрос «сколько клиент должен заплатить»: выручка, число заказов, заказы без цены. Сколько этот заказ стоил компании — не видно нигде: расход на курьеров и межгород живёт в дашборде одной общей цифрой за период, а в разрезе клиентов межгород не делится вообще (так и написано в докстринге clients() в finance.service.ts). Поэтому нельзя сказать, какой клиент приносит деньги, а какой возит коробки в убыток.

Заказчику нужна юнит-экономика: расход на заказ курьеру и межгородним водителям, причём межгород разносится пропорционально весу заказа от веса, который вёз водитель. Сначала общие цифры по клиентам, затем — при клике по клиенту — те же цифры по каждому заказу. Заодно переделывается окно с заказами: вместо узкой правой панели — широкое окно по центру с настоящей таблицей.

Что выяснено на боевой базе (это определяет решения):

Привязки заказов к рейсам нет. За 01.10–21.10 у заказов, уехавших в транзит, 7 257 плеч и у всех tripId пуст; в transit_trips за октябрь ноль записей. Склады рейсы не создают, поэтому разносить расход можно только по той же схеме, которой уже пользуется дашборд: рейс = уникальная тройка (routeId, direction, день) из событий in_transit, см. transitRunDays() и transitRuns() в finance.service.ts.

Веса есть у всех: у заказов в транзите оплачиваемый вес 78 740,7 кг (фактический 64 885,8 кг), заказов с нулевым оплачиваемым весом нет — развесовка делится без остатка.

Смены сейчас не попадают в прибыль. profit() складывает расход как courier_payouts(status=CALCULATED) + courier_adjustments + transitCost; у посменных курьеров amount = NULL со статусом BY_SHIFT, а courier_shifts не читается ни в profit(), ни в series(), ни в clients(). За 01.10–21.10 это 73 150 000 сум расхода мимо прибыли (сдельных начислений за тот же период 136 350 000, корректировок нет).

Ставки направлений в базе: A Ташкент — Бухоро 1 750 000, B Ташкент — Наманган 1 400 000, C Самарканд — Термиз 1 175 000, D Бухоро — Нукус 1 000 000, одинаково в обе стороны. Истории ставок нет — одно текущее значение на направление.

Разнесение проверено на боевых данных и сходится до копейки: за 01.10–21.10 насчитывается 126 рейсов на 172 925 000 сум, и сумма долей по заказам даёт ровно 172 925 000.

Машины ходят почти пустыми, и юнит-экономика это покажет. Загрузка по направлениям за 01.10–21.10 (дней с рейсом из 21, заказов, оплачиваемых кг):

Решения заказчика (21.10.2026):

окно заказов — широкое модальное по центру с таблицей;
фиксированная смена делится равными долями между заказами курьера за этот день;
межгород разносится по оплачиваемому весу (chargeableWeight), тому же, по которому считаются тариф клиента и ставка курьера;
разносим по дням: берём, какие заказы водитель вёз в этот рейс, и делим ставку по весу именно этих заказов. Сглаживать по периоду заказчик отказался — «почему ты смотришь весь период, а не по дням, какие заказы он возил»;
смены включаются в прибыль дашборда — цифра станет честной, прибыль за октябрь упадёт примерно на 73 млн;
в таблице клиентов — суммы за период, средние «на заказ» уходят в карточки над таблицей и в шапку окна.
1. Как считается себестоимость одного заказа
Курьер. Сумма courier_payouts.amount по заказу (плечи PICKUP/DELIVERY/RETURN, уникальность (orderId, leg)) со статусом CALCULATED, плюс доля смены за каждое плечо со статусом BY_SHIFT. Доля смены: courier_shifts.amount за (courierId, день) делённая на число разных заказов этого курьера за тот день — заказ, который один курьер и забрал, и доставил в один день, получает одну долю, а не две. День берётся в таймзоне компании, тем же выражением, которым смена собирается в rebuildShifts() (courier-payouts.service.ts).

Межгород. Для каждого плеча заказа, которому по индексу соответствует день отправки (правило l.n = least(d.n, l.total) из transitRunDays()), заказ попадает в рейс (routeId, direction, день). Доля = ставка_направления × оплачиваемый_вес_заказа / суммарный_оплачиваемый_вес_всех_заказов_этого_рейса. Знаменатель считается по всем заказам рейса, а не только по заказам выбранного клиента, иначе доля раздувалась бы. У заказа с двумя плечами две доли — они складываются.

Поскольку делим по дням, на полупустом рейсе доля огромна. Чтобы цифру нельзя было прочитать неверно, в детализации рядом с суммой всегда стоит, из чего она получилась: «1 кг из 1 кг · в рейсе был 1 заказ» или «2,4 кг из 1 150 кг · 12 заказов». Отдельного значка не нужно — подпись сама объясняет и большую сумму, и минусовую маржу.

Чего разнести нельзя и что с этим делать:

courier_adjustments (надбавки и удержания) к заказам не привязаны — остаются цифрой периода в дашборде, в юнит-экономику не входят; в октябре их нет;
смены source=MANUAL в день без начислений делить не на что — их сумма остаётся в итоге периода, но не ложится ни на один заказ; показываем это подписью в карточке расхода;
ставка рейса не историзирована: правка ставки направления меняет и прошлые периоды. Пишем это в подписи, как уже написано на странице межгорода.
2. Новый сервис расчёта
Новый модуль backend/src/unit-economics/ — UnitEconomicsModule + unit-economics.service.ts. Отдельный модуль, а не метод в FinanceService, потому что считать должны оба потребителя: PricingModule (сводка и детализация) и FinanceModule (дашборд). Импорт в обе стороны дал бы цикл, импорт общего третьего — нет.

/** Себестоимость одного заказа: из чего она сложилась. */
export interface OrderCost {
  courierPiece: number;    // сдельные начисления
  courierShift: number;    // доля фиксированных смен
  courierTotal: number;
  transit: number;         // доля рейсов межгорода
  orderKg: number;         // оплачиваемый вес заказа
  runKg: number;           // вес рейсов, в которых он ехал
  sharePct: number;        // его доля в этом весе, %
  runs: number;            // в скольких рейсах ехал
}

costByOrder(orderIds: string[]): Promise<Map<string, OrderCost>>;
costByClient(window: { from?: Date; to?: Date; basis?: PricingBasis }):
  Promise<Map<string, { courierTotal: number; transit: number; orders: number }>>;
costByOrder — для детализации (до 5 000 заказов одним запросом), costByClient — агрегат по customerId для сводки и для clients() в дашборде. Оба собираются из трёх блоков сырого SQL ($queryRaw), в одной транзакции не нуждаются.

Блок «рейсы и веса» (ядро; окно событий ограничивается по заказам, а не по периоду отчёта, — заказ может уехать позже, чем создан):

WITH target AS (SELECT unnest($1::text[]) AS "orderId"),
moved AS (                       -- когда заказ уезжал
  SELECT DISTINCT e."orderId", (e."changedAt" AT TIME ZONE $2)::date AS day
  FROM order_events e
  WHERE e.kind = 'STATUS' AND e."toValue" = 'in_transit'
), days AS (
  SELECT "orderId", day, row_number() OVER (PARTITION BY "orderId" ORDER BY day) AS n FROM moved
), legs AS (
  SELECT l."orderId", l."routeId", l.direction,
         row_number() OVER (PARTITION BY l."orderId" ORDER BY l.sequence) AS n,
         count(*) OVER (PARTITION BY l."orderId") AS total
  FROM order_transit_legs l
), member AS (                   -- кто ехал в каком рейсе
  SELECT DISTINCT l."routeId", l.direction, d.day, d."orderId"
  FROM days d JOIN legs l ON l."orderId" = d."orderId" AND l.n = least(d.n, l.total)
), run AS (                      -- вес рейса по всем его заказам
  SELECT m."routeId", m.direction, m.day,
         sum(o."chargeableWeight")::float8 AS kg, count(*) AS orders
  FROM member m JOIN shipox_orders o ON o.id = m."orderId"
  WHERE o.demo = $3
  GROUP BY 1,2,3
)
SELECT m."orderId",
       sum(CASE WHEN r.kg > 0
                THEN (CASE m.direction WHEN 'FORWARD' THEN t."tripCostForward"
                                       ELSE t."tripCostReverse" END)::float8
                     * o."chargeableWeight" / r.kg
                ELSE 0 END)::float8 AS transit,
       sum(r.kg)::float8 AS "runKg", count(*)::int AS runs
FROM member m
JOIN target g ON g."orderId" = m."orderId"
JOIN run r ON r."routeId" = m."routeId" AND r.direction = m.direction AND r.day = m.day
JOIN transit_routes t ON t.id = m."routeId"
JOIN shipox_orders o ON o.id = m."orderId"
GROUP BY 1
Окно moved ограничивается двумя датами, посчитанными заранее: минимальная и максимальная дата события in_transit у заказов из target (отдельный дешёвый запрос по индексу order_events(orderId, changedAt)), — иначе CTE прочитает всю историю событий. Края: заказ без плеч или без события in_transit просто не попадает в результат — расход межгорода 0; рейс с нулевым весом (теоретически) даёт 0, а не деление на ноль; заказ, уехавший дважды, получает две доли — по правилу least.

Блок «сдельные начисления» — sum(amount) по orderId при status='CALCULATED', индекс (orderId, leg).

Блок «доли смен»:

WITH by_shift AS (               -- плечи, оплаченные сменой
  SELECT DISTINCT p."orderId", p."courierId", (p."earnedAt" AT TIME ZONE $2)::date AS day
  FROM courier_payouts p
  WHERE p.status = 'BY_SHIFT' AND p."courierId" IS NOT NULL
    AND p."orderId" = ANY($1::text[])
), day_orders AS (               -- сколько разных заказов у курьера в этот день
  SELECT p."courierId", (p."earnedAt" AT TIME ZONE $2)::date AS day,
         count(DISTINCT p."orderId") AS orders
  FROM courier_payouts p
  WHERE p."courierId" IN (SELECT "courierId" FROM by_shift)
  GROUP BY 1,2
)
SELECT b."orderId", sum(s.amount::float8 / d.orders)::float8 AS "courierShift"
FROM by_shift b
JOIN day_orders d ON d."courierId" = b."courierId" AND d.day = b.day AND d.orders > 0
JOIN courier_shifts s ON s."courierId" = b."courierId" AND s."shiftDate" = b.day
GROUP BY 1
Индексы для всех трёх блоков уже есть: order_events(kind, changedAt) и (orderId, changedAt), order_transit_legs(orderId, sequence), courier_payouts(orderId, leg) и (courierId, earnedAt), courier_shifts(courierId, shiftDate). Новых не требуется.

Ограничения
Пока склады не отмечают отправки машин, рейс остаётся «днём направления»: если в один день по одному направлению ушли две машины, это один рейс по одной ставке, и доли заказов будут вдвое меньше реальных. Появятся записи в transit_trips — развесовку можно будет считать по tripId, запрос к этому готов: надо будет заменить CTE member на join по tripId.
На полупустых рейсах себестоимость заказа перекрывает его цену в десятки раз (направления C и D), поэтому в таблице клиентов появятся отрицательные прибыли. Это не ошибка расчёта, а повод смотреть на загрузку машин; естественное продолжение — такая же таблица загрузки на странице межгорода, но в эту работу она не входит.
Правка ставки направления меняет юнит-экономику прошлых периодов: истории ставок нет.
Смены MANUAL без начислений за день не ложатся ни на один заказ — их видно только в итоге по периоду.
Надбавки и удержания курьерам к заказам не привязаны и в себестоимость заказа не входят.
